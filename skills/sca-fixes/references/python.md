# SCA fixes: Python (pip, pip-tools, uv, Poetry)

Identify which tool owns the lockfile before changing anything, and use only that tool to regenerate it. Flags vary between tool versions; check `--help` when a command is rejected. Package names and versions below are placeholders.

| Files present | Tool | Lock is regenerated by |
| --- | --- | --- |
| `uv.lock` | uv | `uv lock` |
| `poetry.lock` | Poetry | `poetry lock` / `poetry update` |
| `requirements.in` plus `requirements.txt` with hashes or "autogenerated" header | pip-tools | `pip-compile` |
| `requirements.txt` only, hand-maintained | pip | edit the file |
| `Pipfile.lock` | Pipenv | `pipenv lock` |

## Trace the path

```bash
uv tree --invert --package vulnerable-lib      # uv: who depends on it
poetry show --tree                             # Poetry: full tree
poetry show vulnerable-lib                     # Poetry: version and what requires it
pipdeptree --reverse --packages vulnerable-lib # any environment, if pipdeptree is installed
pip show vulnerable-lib                        # "Required-by" for the installed environment
```

Note whether the package is in a runtime group or only a dev, test or docs group. Dev-only packages do not ship, but they still run on developer machines and in CI.

## Fix options, in order

### 1. Upgrade the direct dependency

Raise the lower bound in the manifest to the lowest fixing version, then relock.

```bash
uv add "vulnerable-lib>=2.4.1"
poetry add "vulnerable-lib@^2.4.1"
```

For pip-tools, edit `requirements.in`, then `pip-compile`.

### 2. Transitive: relock just that package

Often the parent's range already allows the fixed version and only the lock is stale. Upgrade that one package without touching the rest:

```bash
uv lock --upgrade-package vulnerable-lib
poetry update vulnerable-lib
pip-compile --upgrade-package vulnerable-lib
```

This is the smallest possible change. Try it before anything else for transitive findings.

### 3. Transitive: upgrade the parent

If the parent pins or caps the vulnerable package below the fix, upgrade the parent to a release that allows it, then relock.

### 4. Force the transitive version

When no parent release allows the fix, add a constraint. A constraint limits the version without making the package a direct dependency.

uv, in `pyproject.toml`:

```toml
[tool.uv]
# GHSA-xxxx-xxxx-xxxx: transitive via parent-lib. Remove when parent-lib >= 5.2 is adopted.
constraint-dependencies = ["vulnerable-lib>=2.4.1"]
```

pip and pip-tools, with a constraints file:

```text
# constraints.txt
# GHSA-xxxx-xxxx-xxxx: transitive via parent-lib. Remove when parent-lib >= 5.2 is adopted.
vulnerable-lib>=2.4.1
```

```bash
pip install -r requirements.txt -c constraints.txt
pip-compile --constraint constraints.txt
```

Poetry has no separate constraint mechanism: add the package as an explicit dependency with the fixed lower bound and a comment saying it is there only to hold the transitive version.

If the parent's metadata forbids the fixed version outright, the resolver will fail. That is a real conflict: report it. uv's `override-dependencies` can force past it, but that ships a combination the parent's maintainers have excluded, so use it only with an explicit decision and a test run that exercises the parent.

### 5. Remove or replace

If the package is unmaintained or barely used, remove it and the code that needs it.

## Verify

```bash
uv sync && uv run pytest
poetry install && poetry run pytest
pip install -r requirements.txt && pytest

uv tree --package vulnerable-lib     # or: pip show vulnerable-lib
```

Confirm the resolved version is at or above the advisory's fixed version, then rescan.

## Scanning

Use the scanner the project or its pipeline already uses, so results match the gate. Free options if none is configured:

```bash
pip-audit                          # the active environment
pip-audit -r requirements.txt      # a requirements file
osv-scanner scan -r .              # reads lockfiles, including uv.lock and poetry.lock
```

`pip-audit --fix` can apply upgrades automatically. Review the result like any other change, and rerun the tests.

## Python-specific cautions

- **Unpinned environments.** A bare `requirements.txt` with no versions means the scanner result depends on when the environment was built. Recommend pinning, but do not introduce a new lock tool as part of a security fix without asking.
- **Several requirement files.** Check `requirements-dev.txt`, `docs/requirements.txt`, `constraints.txt`, Dockerfiles with inline `pip install`, and CI scripts. The finding may come from any of them.
- **Python version support.** A fixed release may drop the interpreter version the project runs. Check `requires-python` before upgrading; if it conflicts, that is a decision to report.
- **Compiled packages.** Upgrades to packages with native extensions can lack wheels for the project's platform and fall back to building from source. Verify the install in the same environment CI uses.
- **Vendored copies.** Code copied into the repository (`_vendor/`, `third_party/`) is invisible to the package manager. Search for it when a scanner flags a path inside the repo.
- **Hash-pinned requirements.** With `--require-hashes`, every changed package needs regenerated hashes. Let the lock tool do it.
- **Framework majors.** Django, SQLAlchemy and Pydantic major upgrades are migrations. Use the patched release of the current supported series instead when one exists.
